## 1. 研究问题（RQ）

| # | 问题 | 为什么值得问 |
|:--:|---|---|
| **RQ1** | 在固定机型上，`nnrt(NPU)` 的**纯推理**是否显著快于 `cpu`？绝对差多少 ms、相对倍数多少？ | 这是"NPU 优化"能否成立的前提 |
| **RQ2** | 在**单次拍照检测**（产品真实用法）下，NPU 的收益还剩多少？ | 单次调用吃不到热缓存，固定开销可能吃掉全部收益——这决定 NPU 对产品有没有意义 |
| **RQ3** | 端到端耗时的**瓶颈在哪一段**：解码+缩放 / RGBA→NCHW / 推理 / NMS？ | 若瓶颈不在推理，NPU 优化天花板很低，靶子要换 |
| **RQ4** | 换用 NPU 后端后，**检测结果是否与 CPU 一致**（数值一致性/精度影响）？ | 后端切换若改变结果，任何"更快"都要附带精度代价说明 |
| **RQ5**（可选，后续） | 有哪些**单变量**优化能显著改善真实用法？（取图分辨率、格式转换、线程配置、量化） | 项目目标含"NPU 优化"，但优化必须先有瓶颈定位 |

## 2. 变量与测量口径（必须先写死，否则数据不可比）

### 2.1 自变量（IV）

`backend ∈ { nnrt(NPU), cpu }`，由检测器构造参数强制指定，**不依赖自动回退**（回退会让 A 组混入 B 组样本）。

### 2.2 因变量（DV）

| 指标 | 定义（写死） | 角色 |
|---|---|---|
| `infer_ms` | **仅** `model.predict()` 前后时间差 | **主指标**（RQ1） |
| `e2e_ms` | `detect()` 全程：解码+缩放+转 NCHW+推理+NMS | 次指标（RQ2） |
| `cold_ms` | 进程内**第 1 次**调用的 `infer_ms` | 冷启动开销 |
| 分段耗时 | `t_decode` / `t_convert` / `t_infer` / `t_nms` 四段 | RQ3 |
| 一致性指标 | 同图两后端的：框数、类别集合、匹配框 IoU、分数差 | RQ4 |

> **口径纪律**：`infer_ms` 与 `e2e_ms` **永不同框比较**。此前出现过的"快 4 倍"类结论，
> 根因就是拿全流程与小图纯推理混比——本设计用命名强制隔离。

### 2.3 控制变量（必须全程不变）

| 控制项 | 固定值 |
|---|---|
| 设备 | MatePad Pro Max 悦享（`GEM-W40` / Kirin T93），**同一台**，不跨设备比较 |
| 模型 | 仓库内 `neu_det_yolov8n.ms`（不做任何转换/量化） |
| 输入 | **固定一张预解码好的输入张量**（320×320×3 float32），不含解码路径 → 消除 I/O 抖动 |
| CPU 配置 | `threadNum=4`、`NO_AFFINITIES`、`preferred_fp16`（与 nnrt 配置差异需在结论中显式声明，见 §5） |
| 构建模式 | 全部实验用同一次构建的 HAP（debug），中途不换包 |
| 阈值 | conf 0.25 / IoU 0.45 / max 30（与产品一致） |
| 应用状态 | 每次测量前 force-stop 重启，避免跨状态污染 |

## 3. 实验矩阵

### E1 后端 A/B（回答 RQ1 + RQ2）

- **设计**：交错块 **ABABAB**，每块：10 次**热身**（不进统计）+ **50 次连续计时**（批内取中位）。
  - 每后端 3 块（A 组 3 + B 组 3），**两个独立会话各做一轮**（检验可重复性）。
- **为什么"50 次连续"**：`Date.now()` 只有 1 ms 精度，若单次 4 ms 则量化误差达 25%。
  批量 50 次把时间窗拉到百毫秒级，量化误差降到 <1%。若设备可用纳秒级时钟则同时记录两种口径互校。
- **冷启动 / 预热曲线（★ 2026-10-14 真机数据后新增）**：
  逐次记录**进程内第 1、2、3 … 10 次** `infer_ms`，**不丢弃**（原先设计是"热身 10 次丢弃"，
  但实测发现前两次各约 415 ms、第三次才降到 16 ms —— 这个冷启动成本本身就是产品关键指标，
  必须单独成表，而不是被当噪声丢掉）。
  实测依据（2026-10-14，云设备 GEM-W40，同一进程 PID 37736）：

  | 次序 | `infer_ms` | 检出 | 备注 |
  |:--:|---|---|---|
  | 1 | **413 ms** | 0 | 疑似 NPU 图编译 |
  | 2 | **419 ms** | 0 | 预热未完成 |
  | 3 | 16 ms | 1 | 进入稳态 |
  | 4 | 14 ms | 0 | 稳态 |

  → 结论方向：**冷启动约 400 ms，稳态 14–19 ms**；二者必须分开报告。

#### ★ 2026-10-14 补测后修正：成本不是两档，而是**至少三档**，且与「距上次推理的间隔」强相关

同机补测（进程 55080，同一设备、同一模型、同一张 200×200 图）：

| 条件 | `infer_ms` | 样本 |
|---|---|---|
| 设备/模型**首次**推理（进程 37736 第 1–2 次） | **413 / 419 ms** | 2 |
| **空闲 ~2.7 分钟后**首次 | **71 ms** | 1 |
| 空闲 ~10–18 秒后 | 14 / 16 ms | 2 |
| **连续调用（间隔 ~0.7 秒）** | **4 / 5 / 5 / 5 / 5 / 5 / 6 / 5 ms** | 8 |

**关键推论（待验证）**：存在一个**「热态」窗口**，间隔越短越快；`4–6 ms` 只在连续调用时可达。
→ **因此 `4–6 ms` 不能代表产品体验**：真实用法是"拍一张 → 隔数秒~数分钟 → 再拍一张"，
落点更可能在 **15–70 ms** 一档。（这正是本项目此前"跨口径比较"错误的另一种变体，必须避免。）

**新增必需子实验 E1b：空闲间隔扫描（回答 RQ2 的核心）**

固定同一张图、同一进程，按下表的间隔各测 1 次，每档重复 5 次取中位：

| 间隔档 | 0.5 s | 2 s | 5 s | 10 s | 30 s | 60 s | 120 s |
|:--:|---|---|---|---|---|---|---|
| 记录 | `infer_ms` + `e2e_ms` | … | … | … | … | … | … |

预期产出：一条「间隔 → 纯推理耗时」衰减曲线，据此判定**产品真实用法落在哪一档**，
并据此决定 O5（启动/按需预热）是否值得做、以及预热能挽回多少。
- **单次真实用法**：单独一组，测"隔 3 秒调用一次"（模拟拍照）的 `infer_ms`，用于回答 RQ2。
- **样本量**：每后端每会话 3 块 × 50 = 150 次稳态样本；两会话共 300 次。真实用法组各 20 次。
- **证伪条件（预注册）**：
  - 若 nnrt 稳态 `infer_ms` 中位数与 cpu 的差异 **< 15%** → 判"无实质差异"；
  - 若单次用法组的差距 **< 稳态差距的一半** → 判"固定开销主导，NPU 对当前产品形态无收益"。

### E2 分段打点（回答 RQ3）

- **设计**：对**两种输入**各跑 20 次，记录四段耗时：
  ① 数据集小图（200×200，产品内置图库路径）；② 相机大图规格（4160×3120，占位图）。
- **证伪条件**：若"前后处理"（decode+convert+nms）占比 < 50%，则"瓶颈在前后处理"的假设不成立，
  E5 的优化优先级需整体重排。
- **注意**：该实验用真实 `detect()` 路径（含解码），与 E1 的纯推理口径**分开报告**。

### E3 后端一致性（回答 RQ4）

- **样本**：6 类各 5 张，共 30 张固定图（数据集内置图库，文件名写死入档）。
- **做法**：同一张图分别用两后端各跑 1 次，逐图记录：检出框数、类别集合、每框分数与归一化坐标。
- **指标**：框数一致率、类别集合一致率、匹配框（IoU>0.5）的平均 IoU、平均分数差。
- **证伪条件**：若 **>10% 的图片**出现框数或类别集合不一致 → 判"后端影响检测结果"，
  后续所有 NPU 速度结论都必须附带一致性说明。

### E4 应用级检出抽检（回答 RQ4 的精度延伸）

- **口径声明**：这是**应用级**检出统计，**不等于**训练侧 mAP（NMS/阈值/输入尺寸都不同），
  报告中不得写成 mAP。
- **样本**：默认取 60 张（每类 10 张，固定名单入档）；若数据出口支持批量导出，再扩到
  训练侧 val 划分（划分可复现：`prepare_dataset.py` 固定种子，需按脚本重建名单）。
- **指标**：每类检出图片占比、明显误检数（人工看图判定）、漏检数（对照 NEU-DET 标注）。
- **前置依赖**：见 §7 数据出口。

### E5 优化候选（回答 RQ5，按单变量逐个测）

| 序号 | 候选 | 预期作用段 | 风险 |
|:--:|---|---|---|
| O1 | 取图时限制解码尺寸（大图先缩到必要尺寸） | t_decode | 低 |
| O2 | `toModelInput()` RGBA→NCHW 循环优化（当前逐像素 102,400 次） | t_convert | 低 |
| O3 | CPU 线程数 / nnrt 性能模式调参 | t_infer | 低 |
| O4 | INT8 量化模型 | t_infer | **高（改变精度，需重跑 E3/E4）** |

每项单独改、单独测，**一次只动一个变量**；O4 必须与精度实验绑定，不可只报速度。

## 4. 方法学纪律（针对既往结论不成立的两类根因）

| 纪律 | 具体做法 |
|---|---|
| **禁止跨口径比较** | `infer_ms` / `e2e_ms` / 分段耗时三类指标各自独立成表，不混算倍数 |
| **禁止跨设备比较** | 全部结论限定在 GEM-W40；不同机型数据只能平行列出，不做倍数推断 |
| **单变量原则** | 任何对比只允许一个变量不同（后端 / 分辨率 / 线程数 / 模型），其余全部固定并写入记录 |
| **交错顺序 + 随机化** | ABAB 交错抵消热漂移；每个会话随机决定先跑 A 还是 B |
| **预注册分析口径** | 本文件 §3 的样本量、指标、证伪条件在开跑前确定，跑完不得改判据 |
| **原始数据留存** | 每条计时日志（不只是汇总）落盘归档；汇总可由原始数据重算 |
| **否定结论同样入档** | "不成立/无差异"必须如实记录，不得只留正向结果 |

## 5. 效度威胁与对策

| # | 威胁 | 影响 | 对策 |
|:--:|---|---|---|
| 1 | **热漂移/降频**（60 分钟会话内） | 后跑的组偏慢 | ABAB 交错 + 每块间留 10 s 静置 + 记录块时间戳；两会话复测 |
| 2 | **时钟分辨率**（`Date.now()` 1 ms，测量对象 4 ms 级） | 单次测量误差达 25% | 批量 50 次计时；若可则并用纳秒时钟互校 |
| 3 | **配置不对称**：cpu 用 4 线程+fp16，nnrt 用 HIGH/HIGH 优先级 | 比较的是"两套配置"而非"纯硬件" | 结论中显式声明；补一组"cpu 同优先级/更多线程"的敏感性测试 |
| 4 | **模型/引擎版本倒挂**（模型由 2.10 转出、设备引擎 2.7） | 可能压低或抬高 NPU 表现 | 记录在案；O4 阶段再评估换版本转换的模型 |
| 5 | **远程云调试的额外开销**（投屏、shell、日志） | 增加调度抖动 | 计时在应用进程内完成，不经远程链路；同会话内与 CPU 组同条件 |
| 6 | **debug 构建比 release 慢** | 绝对值偏大 | 全部实验同一构建，只比**相对差**；绝对 ms 标注"debug 构建" |
| 7 | **NPU 首次图编译** | 首帧异常慢 | 10 次热身丢弃；冷启动单独报告 |
| 8 | **单设备、单模型** | 结论不可外推 | 结论中限定适用范围；不外推为"华为平板普遍规律" |
| 9 | **人工看图判定误检/漏检** | 主观性 | 固定判定人、固定标准（框与标注 IoU≥0.5 算命中）、保留截图 |

## 8. 会话预算与执行顺序（每次申请 60 分钟）

| 会话 | 内容 | 关键产出 |
|:--:|---|---|
| **A**（60 min） | P0-1 装包跑通（含"debug 签名包能否直接安装"**当场验证**）＋ P0-2 数据出口验证 ＋ 设备指纹 ＋ E1 首轮 | 能否跑起来的结论、BENCH 首轮数据 |

## 9. 判定规则与交付物

**判定示例（预注册，跑完不改）**

| 结论 | 成立条件 |
|---|---|
| NPU 稳态有收益 | nnrt 稳态中位 `infer_ms` ≤ cpu 的 85%，且方向在 ≥4/6 块中一致 |
| NPU 对产品无收益 | 单次用法组差距 < 稳态差距的一半 |
| 瓶颈在前后处理 | 前后处理占 `e2e_ms` ≥ 50% |
| 后端改变结果 | >10% 样本的框数/类别集合不一致 |

**交付物**

1. 原始日志归档（每条 BENCH 记录）；
2. 汇总表：按后端 × 会话 × 块的 `infer_ms` / `e2e_ms` 中位数、四分位、最小值、最大值；
3. 结论表：RQ1–RQ5 逐条给"成立 / 不成立 / 未验证"，**含否定结论**；
4. 复现步骤：从出包到取数的完整命令序列（并入《AGC云调试-复现步骤.md》）。
