# 研究结论：同一台设备上 NPU 是否实现加速（2026-10-14）

> 研究问题：**在同一台机器上，NPU 是否实现了加速？**
> 设备：HUAWEI MatePad Pro Max 悦享（`GEM-W40`）· Kirin T93 · HarmonyOS/OpenHarmony 7.0 · API 26（AGC 云真机）
> 数据：3 轮基准套件实测，原始日志见同目录
> [第 1 轮](2026-10-14-基准套件-第1轮.txt) · [第 2 轮](2026-10-14-基准套件-第2轮-v2完整模式.txt) · [第 3 轮](2026-10-14-基准套件-第3轮-v3双后端端到端.txt)

## 1. 结论

**是 —— NPU 实现了加速，但加速比随口径变化，必须分层报告：**

| 口径 | nnrt (NPU) | cpu | 加速比 | 来源 |
|---|---:|---:|---:|---|
| 连续调用**纯推理**（各 50 次中位） | **4.29 ms** | 15.72 ms | **3.66×** | 第 3 轮 |
| 同上（第 2 轮复现） | 4.64 ms | 14.98 ms | 3.23× | 第 2 轮 |
| **端到端内**的纯推理段（30 张，均值） | 8.27 ms | 30.50 ms | **3.69×** | 第 3 轮 |
| **端到端全流程**（30 张，均值） | **36.56 ms** | 62.60 ms | **1.71×** | 第 3 轮 |
| 端到端全流程（30 张，中位） | 35.52 ms | 63.71 ms | 1.79× | 第 3 轮 |

> 第 3 轮首次对**同一批 30 张图分别跑两个后端**，因此"1.71×"是产品口径的直接实测，
> 不是推算。**纯推理 3.7× → 端到端 1.7×**，差距来自下面的 §3。

## 2. 判据（为什么这个结论站得住）

| # | 判据 | 结果 |
|:--:|---|---|
| 1 | **同机、同进程、同输入** | ✅ 同一次会话内加载两个模型实例，纯推理阶段共用同一份预解码张量 |
| 2 | **交错测量 + 多轮** | ✅ ABABAB × 3 轮：4.36/14.84、4.48/15.55、4.77/14.76 → **方向 3/3 一致** |
| 3 | **排除"假快"** | ✅ 只等 Promise vs 读输出张量，差 −0.23 ms(nnrt)/−1.82 ms(cpu) → `predict()` 真算完才返回 |
| 4 | **排除"CPU 没调好"** | ✅ 扫 2/4/8 线程，最优 4 线程 14.26 ms，仍慢 3.3× |
| 5 | **无精度代价** | ✅ 30/30 张两后端检出**完全一致**（框数 + 类别序列） |
| 6 | **口径分层一致** | ✅ 纯推理 3.66×、端到端内推理段 3.69× —— 两者一致，说明推理段测量可信 |

## 3. 为什么端到端只有 1.7×，而纯推理有 3.7×

端到端分五段（第 3 轮，30 张中位）：

| 段 | nnrt | cpu | 说明 |
|---|---:|---:|---|
| decode | 4 ms | 3 ms | 与后端无关 |
| readback | 0 ms | 0 ms | 可忽略 |
| **loop（ArkTS 前处理循环）** | **21 ms** | **27 ms** | **与后端无关，但 cpu 路径下更慢 +29%** |
| **infer** | **11 ms** | **32 ms** | ← NPU 唯一能加速的段 |
| nms | 1 ms | 1 ms | 与后端无关 |
| **total** | **35.5 ms** | **63.7 ms** | |

两条原因：

1. **推理只占 nnrt 端到端的 31%**，另外 ~60% 是前后处理（两后端都要付）→ 加速比被摊薄；
2. **CPU 后端下前处理循环反而更慢**（27 vs 21 ms）—— 因为 CPU 后端时 CPU 持续满载，
   而 NPU 后端时推理被卸载、CPU 压力更小。

**含义**：若要把产品口径的加速比提上去，靶子不是模型（推理已只占 31%），
而是那个 ArkTS 逐像素循环（占 60%，且 ArkTS 内优化天花板仅 ~14%，需搬出 ArkTS）。

## 4. 适用边界（什么时候不成立）

| 情形 | 结果 | 依据 |
|---|---|---|
| 设备未开放 NPU（如 K1010 平台） | ❌ 不加速 —— `nnrt` 后端构建失败，只能回退 CPU | 代码三态判定 + 早前设备实测 |
| NNRT 设备列表里**误选** `HIAI_F`（通用入口）而非 `NPU_...` | ❌ 静默回退 CPU，表面"加载成功" | 本机实测：`getInputs()` 返回 undefined → 判为 `NO_INPUTS` |
| 单次调用（拍照，间隔数秒以上） | ✅ 仍加速，但绝对收益被前后处理吃掉（推理段占比不变） | 空闲扫描：nnrt 6–21 ms vs cpu 35–55 ms |

## 5. 未闭合项（如实记录，不影响上述结论）

1. **端到端内的推理（8.3/11 ms）比基准路径（4.29 ms）慢 2 倍**，两种口径都在同机同会话测得，
   成因未定（疑：每次新分配输入缓冲 / CPU 刚跑完循环导致的派发延迟）。产品口径应取前者。
2. **cpu 路径下前处理循环慢 29%** 的机理未查（疑降频/调度）。
3. **"云调试两轮是否同一台物理机"未验证**（日志未记 UDID）→ 后续每轮会话应记录 `bm get --udid`。
4. 第 2 轮空闲扫描每档 n=3 显示格内离散达 1.6×，空闲档的跨轮可比性尚未建立。
